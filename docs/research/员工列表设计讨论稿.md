# "机器人 vs 智能体"设计讨论稿：从角色优先到员工优先

**日期：** 2026-10-15
**性质：** 设计讨论（本轮不实施）
**触发：** 用户实测反馈——术语不统一（智能体/机器人混用）、感觉产品"更像角色而非人"、Orkas 原设计是"内置角色开箱即用"、50 机器人一人公司演示时"点机器人应该看到 50 个员工的列表"但实际只显示对话过的、脑暴"创建机器人是否应与创建智能体分开/基于内置智能体创建/组织架构管理"

---

## 一、先给结论

1. **你的直觉被三家对标产品集体验证**：Grok Bot 的核心设计决策就是"**主对象是机器人，不是会话**"（官方原话："Chats are disposable… the main objects in Grok Bot are Bots"）；其产品页演示侧栏就是一张**一人公司的员工名单**（Chief / Sales Outbound / Inbox Manager / Account Manager / Talent Scout / Expense Manager / Offsite crew）——和你脑暴的"50 个机器人的一人公司"是同一个画面。
2. **但不要把"机器人"和"智能体"做成两个数据实体**——那会撕裂数据模型。正解是：**一个实体、两种呈现 + 术语统一**。智能体（Orkas 的 agent）本来就该被理解为"已入职的员工"，只是现在的界面把它呈现成了"岗位/角色"，且导航上员工列表不可见。
3. **"创建机器人 vs 创建智能体分开"的正确形态不是两个创建流，而是两层隐喻**：AI 团队页 = **岗位/角色库**（内置智能体 = 岗位模板，供"招聘"参考）；消息上下文里"+ 新建机器人" = **入职**（同一个表单，叙事不同：从岗位实例化为有身份的员工）。Grok Bot 的 Marketplace→Add、Hermes 的 Duplicate、Muse 的 SOUL.md 都是"角色模板 → 实例化员工"这一层关系的不同实现。

## 二、术语统一（先解决表层）

现状盘点：中栏过滤器"机器人"、成员面板"编队成员/N 个智能体"、AI 团队页"智能体"、欢迎语"智能体"、飞书截图里飞书自己也是"智能体/机器人/官方"三个 chip 混用——**飞书混用是因为它们确实是三种来源不同的 bot；我们混用则只是继承自 Orkas 的用词不一致**。

建议（对齐"机器人版飞书"定位）：
- **用户可见层统一为"机器人"**：中栏过滤器、成员面板、副行"N 个机器人"、欢迎语、引导页
- **"智能体"保留在管理页**（AI 团队 → 可改称"机器人团队"或"岗位库"）作为能力层术语，或干脆全体统一为机器人
- 纯字符串替换 + i18n 键值梳理，零后端影响，半小时级

## 三、核心调整：员工列表（中栏机器人 tab 的重构）

### 3.1 你踩到的坑的机制

中栏"机器人"过滤器现在过滤的是**会话**——而会话只有对话过才存在。所以：
- 首次点击"机器人" tab → 空（没有任何机器人聊过天）
- 演示 50 机器人公司 → 看不到 50 个员工，只看到聊过的几个

### 3.2 调整方案：机器人 tab 从"会话过滤器"升级为"员工列表"

- 数据源从 conversations 换成 **agents 列表**（主进程已有 agents.list IPC）——**所有机器人都在**，包括从未对话的
- 每行：头像（+P2 状态环：执行中脉冲/空闲）+ 名字 + 角色（profile.role）+ 副行（所属编队/最近活跃/累计消耗）
- **点击机器人 = 打开/自动创建与它的私聊**（createConversation 支持 agentId 绑定，能力现成）——这就是"走到员工桌前跟他说话"
- 未对话过的机器人行显示"还没聊过——说句话即可派活"的引导副行
- 后端影响：**低**。agents.list 已有；"自动创建私聊会话"用的 createConversation(agentId) 是现成 API；唯一的新增是"机器人 tab 数据聚合"的轻量 IPC（把 agents + 运行状态 + 编队归属拼一屏）

### 3.3 这正是 Grok Bot 的立项逻辑

Grok Bot 官方设计博客的核心决策："会话是一次性的，机器人是持久的"——用户回来时找的是"那个销售机器人"，而不是"五天前那段对话"。你的"员工列表"直觉与此完全一致；Orkas 的继承架构（会话优先）是它企业工作台基因的残留，我们已经在三栏改造时把形态掰过来了，这一步是把**导航的对象模型**也掰过来。

## 四、创建流的重构：岗位库 vs 入职

### 4.1 回答"创建机器人和创建智能体要不要分开"

**不分开表单，分开叙事与入口**：

| 入口 | 叙事 | 表单差异 |
|---|---|---|
| AI 团队页 → 创建（岗位库语境） | "添加一个岗位角色" | 同现有表单 |
| 中栏/机器人列表 → ＋ 新建机器人（入职语境） | "招聘一个机器人员工" | 同一表单，默认 interactive=true，创建后自动开私聊 |

同一个表单组件，两个入口的默认值和文案不同。**Grok Bot 的 Marketplace 就是这个模型**：市场里的 bot 是"角色模板"，点 Add 实例化为自己的（带独立记忆）；从零创建也是同一个表单。

### 4.2 "基于内置智能体创建机器人" = 已有能力的新叙事

Orkas 的 16 个内置智能体（DeepResearcher/ContentWriter/ECommerce 系列等）就是现成的岗位模板。调整：
- 机器人列表空状态/创建表单里加"**从岗位库选择**"入口 → 选中内置角色 → 预填表单（role/description/skills 全带）→ 用户只改名字（比如"销售部-小王"）→ 入职
- 技术上 = 把现有 marketplace 安装/复制 agent 的能力挂到创建表单的一个 tab，低-中工作量

### 4.3 编队模板的联动（关键的差异化）

编队模板导入时，**给这批机器人打上"所属编队"元数据**（导入器天然知道这一批是一队的）——员工列表就能按编队分组显示（研发组/销售组/内容组），这是 Grok Bot 的 Groups 分区 + Hermes 的 Groups 的合体，也是 P3 编队库的地基。改动点：导入器给 agent 元数据加 `fleet_id` 字段（低）。

## 五、员工卡片与组织架构（你脑暴的延伸）

员工列表有了之后，自然长出：

1. **员工卡片增强**（点机器人行展开详情）：状态灯（已有信号）、累计消耗（usage ledger v2 按 actor 归因——中等工作量，W5）、所属编队、例行任务数、最近交付物——Grok Bot 的 bot 信息面板同构
2. **组织架构视图**：编队 = 部门，机器人 = 员工，指挥官 = 管理者——一张 org 图就是**最好的演示素材**（"这是我一人公司的组织架构，全员 AI"）。纯 renderer 可做（数据：members + agents + fleet_id），建议 P3 与编队库一起做
3. **主动汇报**（Muse 模式）：机器人完成后台任务主动进群汇报 + 低紧迫建议进工作台 Ideas 区——auto_tasks 已有后台执行能力，缺的是"汇报到群"的 UI 通道，中等工作量

**明确不建议做的**（Cue 式独立身份）：给每个机器人配 email/电话/钱包——本地优先的一人公司用不上，涉运营商与支付合规，成本极高。Cue 验证的是"身份感"的定价能力，不是必需功能。

## 六、与现有开发节奏的合并

| 项 | 归属 | 工作量 |
|---|---|---|
| 术语统一（机器人/智能体梳理） | 字符串 | 半天 |
| 中栏机器人 tab = 员工列表（含未对话机器人 + 点击建私聊） | renderer + 轻量 IPC | 2-3 天 |
| 编队导入打 fleet_id 标签 + 员工列表按编队分组 | 导入器小改 | 1 天 |
| 创建流"岗位库→入职"叙事 | 表单入口/文案 | 1 天 |
| 员工卡片增强（成本/例程/交付物聚合） | usage ledger v2 actor 归因 | 2-3 天（W5） |
| 组织架构视图 | renderer（数据现成） | P3 与编队库合并做 |

**建议**：术语统一 + 员工列表这两项并入下一轮（与 P3 编队库天然耦合，一起做顺）；员工卡片成本归因维持 W5 计划。
