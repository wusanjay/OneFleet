## 一、核心理念层（先对齐价值观，再谈功能）

### 1. 组织化隐喻贯穿始终
Matrix 把多 Agent 协作塑造成「公司」：CEO Office（总协调）→ 部门（专业职能）→ worker agents（执行者），用 OKR（目标→关键结果→任务→执行者）串起执行链。
**对 OneFleet**：我们的「编队 = 团队」隐喻方向一致，但 Matrix 多了**纵向层级**（指挥官不是平级群成员，而是有明确路由职责的管理者）。值得强化：指挥官的职责描述应包含「拆解目标 · 路由给谁 · 汇总交付」，员工卡片应显示「我归哪个编队、我的职责边界」。

### 2. 没有证据，就不算完成
Matrix 的引导页原话：「任务不是因为生成了文件就算完成。只有当它的验收标准（Criteria）被真实的证据（Proof）满足、且负责的领队 Agent 记录了一次检入（Check-in），才算完成。」
连空状态文案都在贯彻：「暂无任务。请让主管定义能够带证据的最小下一步行动。」
**对 OneFleet**：这是 AI 工作台建立信任的根基。任务完成状态必须由「验收标准 + 产物 + Check-in」驱动，而不是模型自评。

### 3. 主动推进与人类确认的边界
Proactive 模式下公司可以自动推进（上游团队完成 KR，下游团队自动接力），但**派发关键动作前先请求用户确认**（实测：「要现在就向两个部门下发启动简报吗？确认后我立即派发」）。
**对 OneFleet**：与我们的「自动化 + 微信推送」规划天然契合——确认请求本身可以推到微信，形成「手机批准、家里开工」闭环。

### 4. 不打扰原则
通知四类事件（需要处理/任务完成/定时任务变更/定时任务执行）**默认全部关闭**，用户显式订阅。Agent 能力开关（浏览器、电脑控制）也默认关。
**对 OneFleet**：微信推送尤其要克制——默认不推，用户在设置里逐类开启，否则会变成骚扰源。

## 二、功能与交互借鉴（按优先级）

### P0-1 执行过程「叙述化 + 渐进披露」
- **Matrix 做法**：执行中 = 中文进度叙述（「状态干净——全公司还没有任何 Objective」「目标已建好（objective-a1）」）穿插可折叠的工具调用卡片（「使用了 2 个工具，并思考了 1 次」「Update plan」）；思考阶段可展开看完整执行计划（含工具名、部门 ID）。
- **OneFleet 现状**：执行中只有 running-card + 计时器，用户看不到「正在做什么」。
- **建议**：turn 流式输出中区分「叙述文本」与「工具调用事件」两类块；工具调用折叠为一行卡片，点击展开参数与结果；运行中允许随时展开/收起。renderer 已有 chat-artifact / interactive-cli 基础，改造成本可控。

### P0-2 任务卡绑定「验收标准 + 产物 + Check-in」
- **Matrix 做法**：KR 卡显示负责部门头像、量化指标、截止日徽章；详情抽屉有目标状态 / 关联 Objective / 负责人 / 进展（Not reported）/ 任务区 / Lead Agent；完成需 Proof + Check-in。
- **OneFleet 现状**：任务只有「执行中/完成」，交付物散在会话流里；无验收概念。
- **建议**：任务卡增加三个字段：`验收标准`（创建时由指挥官生成或用户填写）、`产物`（关联 artifact 卡片）、`Check-in`（机器人自报进度 + 用户确认按钮）。状态机：进行中 → 待验收 → 已完成/需返工。「需返工」要保留上下文可继续对话。

### P0-3 拆解后「先给分派方案，确认再执行」
- **Matrix 做法**：CEO 建完 OKR 不自动派发，列出分派方案请求确认。
- **OneFleet 建议**：指挥官收到目标后，先输出「计划卡」（谁做什么、预计交付什么、何时交付），用户点「开工」才真正分派；plan-first 合同我们已有，把它产品化为**可确认的卡片**而非纯文本。确认动作支持应用内 + 微信远程批准。

### P1-1 权限三级模型，按 Agent 独立设置
- **Matrix 做法**：每个部门独立选「每次询问 / 替我批准 / 完全访问」；设备权限（日历/辅助功能/屏幕录制）逐项说明「仅在…时需要」，申请系统权限前先在应用内解释。
- **OneFleet 现状**：已有 bash_permission，但是全局性。
- **建议**：升级为按机器人的策略表；执行命令类操作继承三级模型；屏幕录制、辅助功能等 macOS 权限在申请前给应用内说明页。

### P1-2 通知分类订阅
- **Matrix 做法**：四类分开、默认全关、每类一句话说明触发时机。
- **OneFleet 建议**：推送设置按「需要我处理 / 任务完成 / 编队状态变更 / 定时任务执行」四类；微信渠道与应用内通知分开订阅；推送内容控制在一句摘要 + 点击跳转。

### P1-3 空状态 = 解释原因 + 行动按钮
- **Matrix 做法**：「没有任务 / 当前 Key Result 需要显式执行时创建一个 / ＋新建任务」；「No automations yet / Create one from a time schedule or an App event」。
- **OneFleet 建议**：全面检查空状态文案：midbar-fleets-empty、employees-empty、资料库、应用等，统一为「为什么是空的 + 下一步动作按钮」。

### P1-4 BYOK 首次可用路径要可靠（反面教训）
Matrix 的添加模型按钮一度无响应、credits 阻塞卡片配置成功后不消失、模型选择器显示与实际不符——三条都发生在**新用户第一次接模型**的关键路径上。
**对 OneFleet**：模型配置是我们的第一转化节点，必须保证：添加表单必达、保存后全局状态即时刷新（所有 composer 的模型显示同步）、连通性测试结果可视化（Matrix 的绿色状态点是好设计）。

### P2-1 状态灯语义系统
头像右上角状态灯：灰=空闲、紫=工作中（呼吸动画）、绿=已完成、红=错误。中栏列表一眼看出全员状态。
**OneFleet 现状**：员工列表已有 status-dot，保持并确保各状态都有真实数据通路（working 状态要真的在任务执行时亮起）。

### P2-2 量化徽章
截止日、指标徽章化（「11-15 截止」「≥20 项」「6.2折」），目标一眼可读。
**建议**：任务卡与编队卡的时间/数量信息统一徽章样式。

### P2-3 引导叙事
Matrix 用 4 页全屏引导讲清组织模型（目标→关键结果→任务→执行者；无证据不算完成；Proactive 自动接力），配组织关系图。
**建议**：OneFleet 首次启动可做 3 页引导：编队是什么 → 指挥官怎么工作 → 数据只在本机。原型已有 guide-card 三步卡，可升级为首次运行全屏引导。

### P2-4 市场的信任设计
Matrix 部门模板导入会下载 release ZIP、显示来源（Matrix Official）、说明「从空对话开始」。技能显示来源仓库与已添加状态。
**建议**：OneFleet 未来做技能/编队模板市场时：展示发布者、来源、版本、权限范围、卸载方式；安装动作分级审批（对齐 P1-1 权限模型）。

## 三、Matrix 的瑕疵清单（我们要避免）

| # | 问题 | 实测细节 | OneFleet 对应检查项 |
|---|---|---|---|
| 1 | credits 阻塞卡片配置成功后不消失 | 需发新消息才验证通过 | 状态恢复后 UI 要主动刷新（绑定/模型修复后，阻塞横幅立即消除） |
| 2 | 模型选择器与实际不符 | 底部显示 GPT 5.6 Terra，实际走 glm-5.3 | composer 模型显示必须与真实路由一致 |
| 3 | 添加模型按钮无响应 | 多次点击无效，绕道才成功 | 关键转化路径的每个按钮都要可达、有 hover/click 反馈 |
| 4 | 列表文字截断、中英混排 | 部门市场名称/描述截断 | 长文本省略策略 + 术语表统一 |
| 5 | 蓝图生成 $6.2M MRR 无免责标注 | 用户可能误读为真实数据 | AI 生成的估算/预测必须显式标注「示例/模拟」 |

## 五、一句话总结

Matrix 验证了我们方向正确的三件事：**组织化隐喻、证据化完成、人类控制权**；它给我们最大的启示不是某个功能，而是把这三件事做成了贯穿全局的 UI 语言——执行过程看得见、完成必须有证据、关键动作留给人。

## 六、Claude Duet 增补调研（2026-10-22）

> 调研对象：Claude Duet（Anthropic 主动式个人智能体独立 App，2026-10-21 官宣研究预览）
> 调研方式：官方公告 / 官网 + The Verge、VentureBeat、Engadget、新智元等报道交叉核验；美区 waitlist，未实测
> 赛道背景：Personal Agent 71 天内四巨头全部落子——Grok Bot 08-11 → Meta Muse 09-08 → OpenAI dots 09-29 → Claude Duet 10-21。Duet 负责人 Karan Ahuja 为前 Meta 产品总监（Muse 系），业界称其「Claude 版 Muse」。

### 6.1 产品形态速览

| 维度 | 内容 |
|---|---|
| 形态 | iOS / Android 独立 App + claude.ai 网页端 |
| 模型 | Claude Opus 5.5（Mike Krieger：第一个「判断力足够以合适方式主动做事」的模型） |
| 可用 | 仅美国，Pro / Max waitlist；Team / Enterprise 未开放 |
| 定价 | 预览期不额外收费，但与 Claude 全家**共用额度池**（后台巡检同样消耗） |
| 连接 | 零初始化继承 Claude 账户的记忆 / 技能 / 连接器，6000+ 连接器即开即用 |

### 6.2 核心交互设计（值得借鉴）

1. **晨报（Morning Brief）**：每天早上一条推送 = 今日待拍板清单，且**每件事的下一步已预做好**（申请表已填、$640 费用待批、邮件草稿就绪），用户只剩「批准 / 改一笔 / 驳回」。话术范式：「5 件事在推进，2 件需要你」。
2. **关机不中断**：任务跑在 Duet 自己的云端 VM + 浏览器里；没有现成连接器的网站退化为浏览器直接操作。
3. **跨系统业务流**：Stripe 未付发票 → 催款草稿 → DocuSign 送签；收银 / Shopify / CRM / 工资 / 银行数据汇成每日经营看板（5:30 自动刷新），并**主动发现**流失率 2.6%→3.4%、给出归因与「满 $40 包邮」对策——AI 开始主动提「接下来该试什么」。
4. **打断判断力作为第一卖点**：周末代盯 Slack，只推「值得打断的那一条」，其余留到周一。官方自认早期会误读线程、误判紧急度。
5. **权限三档 + 绝对红线**：发消息 / 付款 / 签文件 / 删除 → 先展示等批准；证券买卖 / 账户间转账 / 访问他人账户 → **批准也不执行**。支付走 Stripe Link 虚拟卡（真实卡号不外露）；模型永不直接接触密码；专属 classifier 拦截最高敏感级信息外泄。

### 6.3 已知限制

- **额度池共享**：后台巡检耗订阅额度，多开监控任务 = token 燃烧，官方无任务级成本预估。
- **接入面**：Microsoft 365 未支持、Slack 功能有限、Google 环境仅 3 个连接（多 Gmail 用户已在抱怨）。
- **治理**：审计日志等企业管控仅在 Enterprise 档，个人预览版无合规兜底。

### 6.4 对 OneFleet 的借鉴（并入上文优先级体系）

- **晨报 = pushText #9 的标准答案**：第一个高价值场景从「确认请求」扩展为「每日晨报」——推的不是通知，而是「N 在推进 / M 需要你 + 每件的下一步已备好」。微信端形态：一条摘要 + 点击跳转应用内批准。
- **确认交互升级（P0-3）**：Matrix 问「要不要做」，Duet 是「做好了等你点头」——把打断成本降到一次点击。计划卡应默认附带预做产物（草稿 / 填好的表单 / 待批费用）。
- **权限模型补红线层（修正 P1-1）**：三级（询问 / 代批 / 完全）之外加「绝对禁止清单」，这是给 B 端客户最硬的安全叙事。
- **支付隔离范式**：未来若做代付 / 电商场景，参考虚拟卡模式——agent 全程不经手真实凭据。
- **差异化再确认**：四巨头全押云端 VM + 生态额度池；OneFleet 的本地优先 + 微信原生 + BYOK 恰好占据对立面（无额度池焦虑；「主动盯梢型」agent 的数据不出本机是最强信任卖点）。
- **窗口期警示**：Grok Bot Team Bots、Duet 的记忆 / 技能继承都在收敛为「越用越懂你的常驻员工」；**「编队 / 组织」是 OneFleet 唯一尚未被巨头直接覆盖的形态**，差异化窗口有限。
